何が問題だったか

problem

パイプライン全体が DAZ ストアの SKU をキーにしていた。daz_db_analyzer.get_all_skus() が WHERE token IS NOT NULL AND token != '' で絞っていたため、SKU を持たないコンテンツは PostgreSQL → SQLite → ChromaDB のどこにも入らなかった。

DAZ Studio の Smart Content ペインは CMS データベースが実体で、Content Library ペインはコンテンツディレクトリの生のフォルダツリー。つまり後者にしか現れないものが丸ごと欠落していた。実 CMS・実ライブラリに接続して測った結果:

ギャップ実測備考
CMS にはあるが token が空の製品43 製品Renderosity 等の他社製品
CMS に登録すら無いディスク上のファイル109,127 件ユーザ向けファイル 264,162 件中 41%、9,814 ディレクトリ
Poser 形式ライブラリ 2 ルート.duf 0 件中身は .pz2/.cr2/.pp2。CMS にも .pz2 は 1,047 件のみ

設計上の制約として、ui/src は未チェックアウトの git submodule(bmf-daz-content-browser-ui)で、手元にはビルド済みの ui/dist しか無い。UI 改造ゼロで成立させることが前提条件になった。結果として「合成 SKU で通常製品と同じ行を作る」方針を採っている。

何を作ったか

design

SQLite の製品行に source 列を足し、3 系統を同一スキーマに正規化した。合成 SKU を使うので、既存の一覧・検索・フィルタ・サムネイル導線がそのまま動く。

sourceSKU 形式由来画像
daz-storeDAZ token従来どおり。daz3d.com をスクレイプストアの CDN
cms-localcms-<product.id>CMS にあるがストア SKU 無しディスク上の隣接 PNG
filesystemfs-<sha1>CMS に無い。ディスク走査で発見ディスク上の隣接 PNG

ストアページが無い製品は、DAZ Studio がアセット横に書く PNG をサムネイルにし、/api/v1/assets/thumbnail 経由で配信する。_format_product() が image_url を組み立てるので、UI から見れば通常の製品と区別がつかない。

ファイルシステム走査の要点

design-scan
  • 対象拡張子 — .duf に加え Poser 形式 10 種。Poser 形式は Runtime/Libraries/** 配下に限定。data/ は除外
  • 入れ子ルートの除去 — このマシンでは My Library とその配下 3 ディレクトリが両方 root 登録されていた。最も浅いものだけ残さないと二重カウントになる
  • ラッパーディレクトリの除去 — 同じ製品が「ルートに統合して展開」と「アーカイブのフォルダごと展開」で二重に入っているケースが多数あった。CMS の正規トップレベル名を使って剥がし、1 製品に畳んでいる(これで 2,933 → 1,580 製品)
  • SKU の安定性 — SKU はパスそのものではなくラッパー除去後の相対パスから作る。片方のコピーを消しても SKU が変わらない

検索結果が常に 500 件で頭打ちになっていた

bug-search-cap
commiteb7bff9
fix"UISearchRequest.max_results の既定値を 500 → 5000"
fixedtrue

/api/v1/search は ChromaDB から近傍 500 件を取得したうえで、その後に min_relevance を掛けていた。500 は該当件数ではなく候補プールの固定サイズなので、実際に何件マッチしようと表示は 500 で止まる。製品が 1,620 件だった頃は露見しにくかったが、3,239 件になって顕在化した。

UI 上では「Min match: any」も「50%+」も揃って 500 件と出て、プールより下を切る「70%+」でだけ本当の件数(2 件)が出る、という不可解な挙動になっていた。UISearchRequest.max_results の既定値を 5000 に上げ、絞り込みをプールサイズではなく閾値が担うようにして解決。

Min match変更前変更後
any5003,239
50%+5003,236
60%+—72
70%+22

50%+ が 3,236 件という数字が示すとおり、埋め込みの類似度は 0.5 前後に大半が集まっている。実用的な絞り込みが起きるのは 60〜70% の帯。実測コストは応答 0.28 秒 → 0.60 秒、ペイロード 270KB → 1.88MB("office" で計測、dress / forest でも同等)。ビルド済み UI は max_results を送らないので、このサーバ側既定値が全ての UI 検索に効く。結果を 1 応答で返してページングはクライアント側という設計なので、製品数が桁違いに増えたらプールを広げるのではなくサーバページングを入れるべき。

引継ぎ文書に書かれていなかった実際の障害が 2 つあった。どちらも「--model を渡すだけで切り替わる」という前提を崩すもの。

  • token_type_ids の決め打ち。 generate_embeddings() は ONNX へ 3 入力を固定で渡していたが、bge-m3 も multilingual-e5-* も XLM-RoBERTa 系でこの入力を持たない。差し替えた瞬間に InvalidArgument: Invalid Feed Input Name: token_type_ids で落ちる。session.get_inputs() を見て、グラフが宣言した入力だけを渡すようにした
  • --model が無効だった。 embedding_utils はモデル ID を import 時 に読んでいたが、main.py は managers.managers 経由でこのモジュールを import した 後 に os.environ を書き換えていた。つまりフラグは常に無視されていた。設定解決を遅延(初回使用時)に変更して解消

  • モデルごとの規約表(_MODEL_CONVENTIONS)。bge-m3 は CLS プーリング、E5 系は query: / passage: 接頭辞。間違えても例外は出ず、黙って質が落ちるだけなので、呼び出し側任せにせずコードに固定した。既定モデルは従来どおり mean プーリング・接頭辞なしのまま(既存インデックスと互換)
  • 未使用だった is_query 引数を接頭辞の切り替えに接続
  • vab.py load --model を追加(従来は server にしか無く、インデックスと検索でモデルがズレうる)
  • export_model.py --model、EMBEDDING_MAX_LENGTH / EMBEDDING_POOLING などの環境変数
  • /api/v1/settings の embedding_model / query_model は実際の推論に一切使われていない飾りだったので、少なくとも EMBEDDING_MODEL_ID を反映して嘘をつかないようにした
