何が問題だったか

パイプライン全体が DAZ ストアの SKU をキーにしていた。daz_db_analyzer.get_all_skus() が WHERE token IS NOT NULL AND token != '' で絞っていたため、SKU を持たないコンテンツは PostgreSQL → SQLite → ChromaDB のどこにも入らなかった。

DAZ Studio の Smart Content ペインは CMS データベースが実体で、Content Library ペインはコンテンツディレクトリの生のフォルダツリー。つまり後者にしか現れないものが丸ごと欠落していた。実 CMS・実ライブラリに接続して測った結果:

設計上の制約

ui/src は未チェックアウトの git submodule（bmf-daz-content-browser-ui）で、手元にはビルド済みの ui/dist しか無い。UI 改造ゼロで成立させることが前提条件になった。結果として「合成 SKU で通常製品と同じ行を作る」方針を採っている。

何を作ったか

SQLite の製品行に source 列を足し、3 系統を同一スキーマに正規化した。合成 SKU を使うので、既存の一覧・検索・フィルタ・サムネイル導線がそのまま動く。

sourceSKU 形式由来画像
daz-store DAZ token 従来どおり。daz3d.com をスクレイプ ストアの CDN
cms-local cms-<product.id> CMS にあるがストア SKU 無し ディスク上の隣接 PNG
filesystem fs-<sha1> CMS に無い。ディスク走査で発見 ディスク上の隣接 PNG

ストアページが無い製品は、DAZ Studio がアセット横に書く PNG をサムネイルにし、/api/v1/assets/thumbnail 経由で配信する。_format_product() が image_url を組み立てるので、UI から見れば通常の製品と区別がつかない。

パイプラインのフェーズ

--phase に scan を追加した。all（既定）は etl → scan → embed の順に実行する。WebUI の Update ボタンは run_update_flow 経由で phase='all' を呼ぶので、ボタン 1 つで全部走る。

ファイルシステム走査の要点

  • 対象拡張子 — .duf に加え Poser 形式 10 種。Poser 形式は Runtime/Libraries/** 配下に限定。data/ は除外。
  • 入れ子ルートの除去 — このマシンでは My Library とその配下 3 ディレクトリが両方 root 登録されていた。最も浅いものだけ残さないと二重カウントになる。
  • ラッパーディレクトリの除去 — 同じ製品が「ルートに統合して展開」と「アーカイブのフォルダごと展開」で二重に入っているケースが多数あった。CMS の正規トップレベル名を使って剥がし、1 製品に畳んでいる（これで 2,933 → 1,580 製品）。
  • SKU の安定性 — SKU はパスそのものではなくラッパー除去後の相対パスから作る。片方のコピーを消しても SKU が変わらない。

途中で直した既存バグ

今回の機能追加とは独立に、元から存在していた不具合を 3 件踏んだので直してある。上流にも同じ問題がある。

サムネイル API がルート順で潰されていた

/api/v1/assets/thumbnail が /api/v1/assets/{sku} より後に宣言されていた。FastAPI は宣言順にマッチするため、全てのサムネイル要求がアセット一覧エンドポイントに流れ、画像ではなく {"sku":"thumbnail","files":[]} を返していた。ストア製品は CDN 画像を使うため露見していなかったが、ローカルサムネイルはこれに依存するので致命的。宣言順を入れ替えて解決。

グルーピングが O(n²) で完走しなかった

merge_into_ancestors() はマージのたびに全ルートを再走査する実装で、未登録 9,814 ディレクトリでは 10 分回しても終わらなかった。パスをトライ木に入れてボトムアップに 1 度だけ走査する方式に書き直し、約 2 秒になった。判定基準（深さ・カテゴリ語の除外）は元の実装と同じ。

cp932 コンソールでインデックス処理ごと落ちる

rich の進捗スピナーが使う点字文字を cp932 が encode できず UnicodeEncodeError で異常終了していた。製品名の en dash でも同様。CLI 起動時に stdout/stderr を errors="replace" で再構成して回避。

このほか、SKU_EXPR をそのまま WHERE に使うと dzcontent.content（70 万行）の全走査になるため、アセット取得は p.token / p.id という索引の効く列で引くようにしてある。製品詳細を開くたびに全走査、という事態は避けられている（実測 0.02 秒）。

検証したこと

  • テスト — pytest tests/ 41 件 green（新規 12 件を含む）。合成ツリーでグルーピング・ラッパー除去・入れ子ルート除去・SKU 安定性を確認。
  • 実データでの ETL — cms-local 43 製品すべて取り込み、43/43 でサムネイル解決。
  • 実データでの走査 — filesystem 1,576 製品を登録。1,542 件（98%）にサムネイルあり。
  • API — /info の内訳、意味検索でローカル製品がヒットすること、/assets/{sku} が fs 製品でディスクからファイルを返すこと、サムネイルが実 PNG（HTTP 200 / image/png）で返ることを確認。
  • UI — ブラウザで表示確認。UI 無改造のまま 3,239 製品が実サムネイル付きで並ぶ。
  • Update ボタン — POST /api/v1/update を実際に叩き、etl → scan → embed が走り差分 0 件で正常終了することを確認。走査中の進捗表示も追加後に再確認済み。
  • DAZ Studio 連携 — Script Server 2.9.0 稼働中に browse-folder を実行し成功。実在したメソッドは browseToPath（browseToFolder/browseToDir は存在せず、候補を並べたフォールバックが効いた）。

環境で注意すべき点

  • .venv に pytest と httpx を追加インストールした。pyproject.toml の依存には入っていない。テスト実行に必要だったため。不要なら pip uninstall pytest httpx で戻せる。
  • bd（beads）は使わない。未インストールで、.beads/ の課題は上流メンテナのもの。CLAUDE.md 冒頭の「Local overrides」節に明記済み（自動生成ブロックの外側なので再生成で消えない）。
  • .env の DAZ_STUDIO_EXE_PATH=CHANGEME は未設定のまま。元からの状態。Script Server 経由の導線は動くので影響は限定的だが、プラグインを止めたときのフォールバック（DAZ Studio を起動して製品を開く）は機能しない。

未着手・判断待ち

判断待ち

  • 上流への PR を出すか。fork がある以上いつでも作れる。出すなら目玉はサムネイルのルート順バグとグルーピングの O(n²) 問題。ただしレビュー対応と上流の設計方針との擦り合わせが継続的に発生する。
  • fork に残っている上流のブランチ 7 本。feature/jit-morph-loader 等。上流に追随しないなら削除してよい。

既知の限界

  • グルーピングの過剰マージが 4 件。ディスク上に製品の境界は存在せず、命名規則からの推定なので必ず誤差が出る。1 製品あたり中央値 32 ファイルと全体は健全だが、最大は Thunder-3D の 8,480 ファイルで、これはベンダーディレクトリごと 1 製品にまとめてしまっている。.env の SCAN_MIN_PRODUCT_DEPTH（既定 5）で調整できる。
  • 物理的に 2 箇所へ展開された製品は別製品として出る場合がある。片方が CMS 登録済み・もう片方が未登録というケース。ディスク上に実際 2 つあるので誤りではないが、一覧では重複に見える。
  • UI の Update ボタンが force をどう送っているか未確認。ui/src が未チェックアウトのため。差分実行（force: false）で動くことは API 経由で確認済み。
  • UI 自体は未改造。source は API が返しているので、submodule を取得すれば「Content Library のみ表示」といったフィルタは追加できる。
